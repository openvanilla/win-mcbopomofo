# Server-Client State Mapping Rules

## 1. Purpose

This document defines how the following three elements in the current system correspond to each other:

- `InputState` internal to the Server
- `IPC::StateUpdatePayload` generated by `ServerUI`
- `CStateEditSession` in the Client

## 2. Data Flow

When the Server state changes, the actual flow is as follows:

1. `KeyHandler` or `InputController` generates a new `InputState`.
2. `InputController::ChangeState()` calls `UIInterface`.
3. `ServerUI::Update()` or `ServerUI::Reset()` projects the state into a `StateUpdatePayload`.
4. The payload returns to the Client via `NamedPipe`.
5. The Client saves it to `_lastState` in `McBopomofoTIP::OnKeyDown()`.
6. The Client creates a `CStateEditSession`.
7. `CStateEditSession::DoEditSession()` executes the following based on the payload:
   - Commit text
   - Create or update the composition
   - Set caret position
   - Update TSF candidate UIElement data
   - Hide or end stale TSF UIElements when the payload no longer has candidates or tooltip text

## 3. Payload Field Semantics

Main fields of `StateUpdatePayload`:

- `commitString`
  Text to be committed directly to the application.
- `composingBuffer`
  Text to be displayed as preedit / composition.
- `cursorIndex`
  UTF-8 cursor offset within the composing buffer.
- `candidateIndex`
  The currently selected index in the candidate list.
- `candidates`
  The list of strings displayed in the candidate window.
- `tooltip`
  Auxiliary text displayed in the tooltip window.
- `markStart`, `markEnd`
  The marking range within the preedit.

`StateUpdatePayload` also contains server-only popup fields, such as
`forceVertical`, `selectionStyle`, `candidateFontSize`, `hint`,
`candidateWindowVertical`, and `candidateWindowColors`. These fields are used by
`ServerPopupController`, `CandidateWindow`, and `TooltipWindow`; they are not
serialized back to the Client in the IPC state update response.

## 4. Server Mapping of Various States

Implementation is located in `ServerUI::Update()` in `src/Server/main.cpp`.

### `Inputting`

- `composingBuffer = inputting->composingBuffer`
- `cursorIndex = inputting->cursorIndex`
- `candidates = []`

Client mapping:

- If a composition does not exist, create a composition.
- Write composing text.
- Set caret position.

### `ChoosingCandidate`

- `composingBuffer = choosing->composingBuffer`
- `cursorIndex = choosing->cursorIndex`
- `candidates = candidate values`

Client mapping:

- Maintain composing text.
- Display candidate window.
- Highlight current item according to `candidateIndex`.

### `SelectingDictionary`

- `composingBuffer = previousState->composingBuffer`
- `candidates = menu`
- server popup projection: `forceVertical = true`

Client mapping:

- Maintain existing preedit.
- Display a vertical candidate list.

### `ShowingCharInfo`

- `composingBuffer = previousState->composingBuffer`
- `candidates = two lines of information strings`
- server popup projection: `forceVertical = true`

### `Marking`

- `composingBuffer = marking->composingBuffer`
- `markStart`, `markEnd` set the marking range.

Client mapping:

- Update composing text.
- Apply marked display attribute.

### `AssociatedPhrases`

- `composingBuffer = assoc->composingBuffer`
- `candidates = list of associated phrases`

### `AssociatedPhrasesPlain`

- `composingBuffer = ""`
- `cursorIndex = 0`
- `candidates = list of associated phrases`

Client mapping:

- Do not create a composition.
- Only display the candidate window.

### `NumberInput`

- `composingBuffer = "[數字] ..."`
- `candidates = list of conversion results`
- server popup projection: `forceVertical = true`

### `Big5`

- `composingBuffer = big5->composingBuffer()`
- `candidates = []`

Client mapping:

- Display preedit.
- Do not display candidate window.

### `IcuTransformInput`

- `composingBuffer = icuTransformInput->composingBuffer`
- `cursorIndex = icuTransformInput->cursorIndex`
- `candidates = icuTransformInput->candidates`
- server popup projection: `forceVertical = true`

Client mapping:

- Display preedit buffer.
- Display candidates window for script transformation options.

### `SelectingFeature`

- `composingBuffer = ""`
- `candidates = feature names`
- server popup projection: `forceVertical = true`

Client mapping:

- Do not create a composition.
- Only display the candidate window.

### `SelectingDateMacro`

- `composingBuffer = ""`
- `candidates = macro menu`
- server popup projection: `forceVertical = true`

Client mapping:

- Do not create a composition.
- Only display the candidate window.

After an item is selected, this state often transitions directly to a commit-only payload.

### `CustomMenu`

- `composingBuffer = customMenu->composingBuffer`
- `candidates = entry names`

## 5. Semantics of `Reset()`

`ServerUI::Reset()` will:

1. Temporarily store the existing `commitString`.
2. Recreate a clean `StateUpdatePayload`.
3. Put the `commitString` back.

This means:

- Reset will clear composing/candidate/tooltip/mark.
- But it will not consume text that is already prepared to be committed.

This is also why the client might receive:

- `commitString != ""`
- `composingBuffer == ""`
- `candidates.empty() == true`

## 6. Client Application Rules

Implementation is located in `src/Client/StateEditSession.cpp`.

### Rule A: Look at `commitString` first

If `commitString` is not empty:

- If there is an existing TSF composition, write using the composition range and then end the composition.
- If there is no composition, call `InsertTextAtSelection` directly.

### Rule B: Then look at `composingBuffer`

If `composingBuffer` is not empty:

- If there is not yet a composition, call `StartComposition` first.
- Update preedit text.
- Set caret position.
- Apply display attributes.

### Rule C: If `composingBuffer` is empty but there is an existing composition

- Clear the range.
- Clear display attributes.
- Call `EndComposition`.

### Rule D: Route candidate / tooltip UI according to payload

- When `tooltip` is not empty, route tooltip visibility/layout to the Server and hide candidates.
- Otherwise, update the TSF candidate UIElement path first. If TSF indicates the TIP should draw its own popup, send layout/visibility to the Server so the Server-owned `CandidateWindow` is shown or updated.

## 7. Special Rules for commit-only payload

If the payload meets the following:

- `commitString != ""`
- `composingBuffer == ""`
- Client side `_pComposition == nullptr`

Then it is treated as a direct commit without composition.

This path has two important restrictions:

1. Hide auxiliary UI before entering the edit session in `McBopomofoTIP::OnKeyDown()`.
2. After committing in `DoEditSession()`, return directly and do not continue operating candidate / tooltip / selection related UI.

The reason is that some TSF hosts, especially the new Notepad, are very sensitive to this type of write edit session.

## 8. Design Principles

If new server states are added in the future, follow this sequence:

1. Define whether it is logically `NotEmpty`.
2. Decide how `ServerUI::Update()` will project it into a payload.
3. Finally, confirm whether the Client should treat it as:
   - composition state
   - candidate-only state
   - commit-only state

Do not work backward by distorting the server state semantics just because of "how the client wants to draw it" (e.g., artificially inserting a fake composing buffer into a candidate-only state).
